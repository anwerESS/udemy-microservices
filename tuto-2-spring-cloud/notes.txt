	- configure a Spring Cloud Config Server:
		* from a class path
			1. In your Config Server project, add the following dependencies to your pom.xml
				<dependency>
					<groupId>org.springframework.cloud</groupId>
					<artifactId>spring-cloud-config-server</artifactId>
				</dependency>
				...
			  <dependencyManagement>
				<dependencies>
				  <dependency>
					<groupId>org.springframework.cloud</groupId>
					<artifactId>spring-cloud-dependencies</artifactId>
					<version>${spring-cloud.version}</version>
					<type>pom</type>
					<scope>import</scope>
				  </dependency>
				</dependencies>
			  </dependencyManagement>
			2.  Enable the Config Server with @EnableConfigServer in main class
			3.  Configure the Config Server to Use Classpath (application.yml)
				server:
				  port: 8888  # Default port for Config Server

				spring:
				  profiles:
					active: native  # Use the "native" profile to load from classpath
				  cloud:
					config:
					  server:
						native:
						  search-locations: classpath:/config  # Look for config files in /config directory on classpath

		* Implementing Cross cutting concerns Tracing & Logging using Gateway (Correlation ID)
			+ Request Tracing:
				When a request enters the system, the RequestTraceFilter checks if it already has a Correlation ID in the headers.
				If not, it generates a new Correlation ID (using a UUID) and adds it to the request headers.
				This ensures that every request has a unique identifier.
			Response Tracing:
				After the request is processed, the ResponseTraceFilter retrieves the Correlation ID from the request headers.
				It adds the Correlation ID to the response headers before sending the response back to the client.
				This ensures that the client (or downstream services) can also trace the request.
			Logging:
				Both filters log the Correlation ID for debugging and monitoring purposes.
				For example:
					RequestTraceFilter logs when a Correlation ID is found or generated.
					ResponseTraceFilter logs when the Correlation ID is added to the response headers.

			.route(p -> p
				.path("/eazybank/loans/**")

										Duration.ofMillis(1000), // Max backoff delay of 1000ms
										2, // Exponential backoff factor of 2
										true // Enables jitter to randomize the backoff time
								)
						)
						/// END RETRY PATERN
				)

	- Rate Limiting in the API Gateway (using Redis) vs Microservice (using Resilience4j and @RateLimiter annotation)
		1. Rate Limiting in the API Gateway (using Redis)
			How It Works:
				The API Gateway (e.g., Spring Cloud Gateway) enforces rate limits using Redis as a centralized store for tracking request counts.
				Each request is checked against the rate limit before being forwarded to the downstream microservice.
				Redis is used to store and synchronize request counts across multiple instances of the Gateway.
			Advantages
				* Centralized Control: Rate limiting is enforced at the edge of the system, ensuring consistent behavior across all microservices.
				* Scalability: Redis allows the rate limiter to scale across multiple Gateway instances.
				* Ease of Implementation: The Gateway handles rate limiting, so individual microservices don’t need to implement their own logic.
				* Global Rate Limits: You can enforce global rate limits (e.g., 1000 requests per second across all users) easily.
			Disadvantages
				* Single Point of Failure: If Redis goes down, rate limiting may fail, potentially overloading the system.
				* Limited Granularity: It’s harder to enforce fine-grained rate limits (e.g., per user, per endpoint) in the Gateway.
				* Latency: Each request requires a call to Redis, which adds some latency.
			Use Cases
				* Global Rate Limiting: Enforcing a global limit on the number of requests per second to protect the entire system.
				* Edge-Level Protection: Protecting the system from abuse or DDoS attacks at the edge (before requests reach the microservices).
				* Simple Rate Limiting: When you need a straightforward, centralized rate-limiting solution.
		2. Rate Limiting in the Microservice (using Resilience4j and @RateLimiter annotation)
			How It Works
				* Each microservice (e.g., Accounts microservice) implements its own rate limiting using Resilience4j.
				* The @RateLimiter annotation is used to apply rate limits to specific methods or endpoints.
				* The rate limiter configuration is defined in the application.yml file.
			Advantages
				* Fine-Grained Control: You can enforce per-user, per-endpoint, or per-service rate limits.
				* Decentralized: Each microservice is responsible for its own rate limiting, reducing dependency on a central component.
				* Flexibility: You can customize rate limits for specific use cases (e.g., stricter limits for sensitive endpoints).
				* No External Dependency: Resilience4j works in-memory, so you don’t need an external store like Redis.
			Disadvantages
				* Complexity: Each microservice must implement and manage its own rate-limiting logic.
				* Inconsistent Limits: If multiple microservices enforce different rate limits, it can lead to inconsistent behavior.
				* Scalability: In-memory rate limiting may not scale well across multiple instances of the same microservice.
			Use Cases
				* Per-User Rate Limiting: Enforcing limits on a per-user basis (e.g., 10 requests per second per user).
				* Endpoint-Specific Limits: Applying stricter limits to sensitive endpoints (e.g., login or payment endpoints).
				* Microservice-Specific Limits: When different microservices have different rate-limiting requirements.

	- Introduction to Bulkhead pattern (not used in this project)
		* there is no support for Bulkhead pattern in gateway, we can only implement it in microservices using Resilience4j lib
		* The Bulkhead Pattern achieves resource isolation by:
			1. Limiting Concurrent Requests:
				Restricting the number of concurrent requests to a specific component or service.
				For example, if a service can handle only 10 requests at a time, the bulkhead ensures that no more than 10 requests are processed simultaneously.
			2. Separating Thread Pools:
				Using separate thread pools for different components or services.
				This ensures that a failure or slowdown in one component does not exhaust resources for other components.
			3.Preventing Cascading Failures:
				If one component fails or becomes slow, the bulkhead ensures that other components continue to function normally
		Why Use the Bulkhead Pattern?
			1. Fault Isolation: Prevents failures in one part of the system from affecting other parts.
			2. Resource Management: Ensures that no single component can exhaust system resources (e.g., threads, connections).
			3. Improved Stability: Makes the system more resilient to failures and high load.
			4. Better Performance: Prevents one slow or failing component from degrading the performance of the entire system.

	- Aspect order of Resiliency patterns (https://resilience4j.readme.io/docs/getting-started-3#aspect-order)
		* Aspect order
			The Resilience4j Aspects order is the following:
				Retry ( CircuitBreaker ( RateLimiter ( TimeLimiter ( Bulkhead ( Function ) ) ) ) )
			so Retry is applied at the end (if needed).
		* If you need a different order, you must use the functional chaining style instead of the Spring annotations style or explicitly set aspect order using the following properties:
			- resilience4j.retry.retryAspectOrder
			- resilience4j.circuitbreaker.circuitBreakerAspectOrder
			- resilience4j.ratelimiter.rateLimiterAspectOrder
			- resilience4j.timelimiter.timeLimiterAspectOrder
			- resilience4j.bulkhead.bulkheadAspectOrder
		* For example - to make Circuit Breaker starts after Retry finish its work you must set retryAspectOrder property to greater value than circuitBreakerAspectOrder value (the higher value = the higher priority).

			  circuitbreaker:
				circuitBreakerAspectOrder: 1
			  retry:
				retryAspectOrder: 2
